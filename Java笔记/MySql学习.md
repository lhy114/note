##### B+树和B树
![[Pasted image 20260806145917.png]]
![[Pasted image 20260806150553.png]]

**这里补充为什么不用红黑树**，在数据库中，瓶颈一般是磁盘的IO，树的每一层相当于每次磁盘访问的次数，如果一个数据库很多，那么构建的这个红黑树，高度会很高（几十层），但是由于B树节点的子节点有很多，所以树的高度会控制的很低，通常也就3-4层高度，那么此时访问的IO次数远远小于红黑树。为什么Java的容器会使用红黑树呢，因此容器是在内存之间，我们访问的速度几乎可以忽略，现在的目标就是，简单实现，然后插入删除稳定，中序遍历有序的效果了。
![[Pasted image 20260806151606.png]]![[Pasted image 20260806151818.png]]
**为什么数据库使用的B+树而不是B树呢？**（对于每一个节点我们都是用一个页）
1. **内部节点小，树才能矮**。由于节点现在不存放数据了，现在我们可以把度设置的很大很大，此时存储的指针就会很多。
2. **范围查询可以顺着叶子节点进行查询。** B+ 树的叶子节点按 key 有序排列，并且彼此用指针串成链表（InnoDB 里是双向链表）。范围查询（`BETWEEN`、`> <`、`ORDER BY`）只要定位到第一个满足条件的叶子，然后顺着链表往下读就行，几乎全是顺序 I/O。
3. **查询性能稳定。** B 树里有些数据在高层，碰巧命中能少读两层；但这是不稳定收益，不能依赖。B+ 树所有查询都必然走到叶子层，路径固定、开销可预期，对数据库执行计划更友好。

##### 索引的分类
![[Pasted image 20260806154936.png]]

**InnoDB的索引分为两类**：
1. **聚集索引**，相当于存储的表的物理结构，将**主键进行排序构造成一个B+树**，然后叶子节点存储的**整条数据记录**。
2. **二级索引**，自己建立的索引，叶子节点现在存储的是当前的**索引列+主键**
![[Pasted image 20260806160233.png]]
![[Pasted image 20260806155814.png]]

**回表查询**，当我们执行 select * from emp where name = 'Army'的时候，首先我们会通过二级索引找到对应的主键值，然后通过主键值，我们才能够通过聚集索引得到数据的信息。
- 主键查询：直接进聚簇索引，最快
- 走二级索引的查询：**只有需要的数据在二级索引里拿不全时**，才需要回表
- 覆盖索引：不需要回表
- 全表扫描：连索引都不走，直接把表（聚簇索引叶子）全读一遍
--------------------------------------------------------------------
- 条件是主键 → 走聚簇索引，不进二级索引
- 条件是非主键列且建了索引 → 走二级索引，可能要回表
- 条件是非主键列且没建索引 → 全表扫描
- 查询返回的列二级索引全覆盖 → 走二级索引但不回表

##### 主键优化插入
1. 首先我们回顾一下整个数据库的组织结构, 在InnoDB中，主键是按照顺序存放的的，这种存储存储的方法，我们常常为B+树（**注意这里会问为什么要采用B+树，而不是二叉树，红黑树，B树**），我们把这种存储的表称之为索引组织表（IOT）。 对于每一个节点我们常常使用一个page进行存储的，每一个页占有大小为16k
![[Pasted image 20260807093709.png]]
2. 为什么我们主键插入的时候尽量是顺序加入，而不是不要乱序加入。
3. 第一个原因就是**页分裂**。（第一张图为顺序，第二章为乱序）
![[Pasted image 20260807094026.png]]
首先50会找到对应的位置，由于前两个页表已经满了，所以这个时候会开辟新的一个页，但是为了满足顺序存储，此时mysql会找到最近的一个页表，拿出一半的数据，存放在3#中，然后将3#页表插入到1# 和 2#页表之间。
![[Pasted image 20260807094113.png]]

4. 页合并，主要处理的是那些删除的数据，InnoDB首先不会直接删除当前的数据，而是先做一个标记，如果当前的页里面的数据被删除的（也就是做了标记）达到50%（阈值），那么此时就找到前后的页看看是否能合并

##### limit 优化
![[Pasted image 20260807101101.png]]

这一章节还是我来进行分析吧，假设id不是主键且没有建立索引
SELECT * FROM t_user ORDER BY id LIMIT 1000000, 20;
如果是上述的sql语句执行，那么会出现回表查询，而且order by会导致mysql首先会进行file sort这一步也就十分耗时，然后在limit 1000000这个阶段，select在limit执行之前，所以还是把所有的数据进行返回。

所以我们的思路就很明确了，首先尽量id建立一个索引，这样我们就不需要把时间耗在sort上。然后select我们不需要前1000000的所有数据，我们要的是后部分的数据，所以select * 前面就可以省略了，因此我们可以采用。

SELECT t.*
FROM t_user t
JOIN (
  SELECT id
  FROM t_user
  ORDER BY id
  LIMIT 1000000, 20 // 先通过id进行查表，返回一个id子表
) tmp ON t.id = tmp.id;// 然后用一个id进行匹配返回dui
