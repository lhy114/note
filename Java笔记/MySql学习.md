##### B+树和B树
![[Pasted image 20260806145917.png]]
![[Pasted image 20260806150553.png]]

**这里补充为什么不用红黑树**，在数据库中，瓶颈一般是磁盘的IO，树的每一层相当于每次磁盘访问的次数，如果一个数据库很多，那么构建的这个红黑树，高度会很高（几十层），但是由于B树节点的子节点有很多，所以树的高度会控制的很低，通常也就3-4层高度，那么此时访问的IO次数远远小于红黑树。为什么Java的容器会使用红黑树呢，因此容器是在内存之间，我们访问的速度几乎可以忽略，现在的目标就是，简单实现，然后插入删除稳定，中序遍历有序的效果了。
![[Pasted image 20260806151606.png]]![[Pasted image 20260806151818.png]]
**为什么数据库使用的B+树而不是B树呢？**（对于每一个节点我们都是用一个页）
1. **内部节点小，树才能矮**。由于节点现在不存放数据了，现在我们可以把度设置的很大很大，此时存储的指针就会很多。
2. **范围查询可以顺着叶子节点进行查询。** B+ 树的叶子节点按 key 有序排列，并且彼此用指针串成链表（InnoDB 里是双向链表）。范围查询（`BETWEEN`、`> <`、`ORDER BY`）只要定位到第一个满足条件的叶子，然后顺着链表往下读就行，几乎全是顺序 I/O。
3. **查询性能稳定。** B 树里有些数据在高层，碰巧命中能少读两层；但这是不稳定收益，不能依赖。B+ 树所有查询都必然走到叶子层，路径固定、开销可预期，对数据库执行计划更友好。

##### 索引的分类
![[Pasted image 20260806154936.png]]

**InnoDB的索引分为两类**：
1. **聚集索引**，相当于存储的表的物理结构，将**主键进行排序构造成一个B+树**，然后叶子节点存储的**整条数据记录**。
2. **二级索引**，自己建立的索引，叶子节点现在存储的是当前的**索引列+主键**
![[Pasted image 20260806160233.png]]
![[Pasted image 20260806155814.png]]

**回表查询**，当我们执行 select * from emp where name = 'Army'的时候，首先我们会通过二级索引找到对应的主键值，然后通过主键值，我们才能够通过聚集索引得到数据的信息。
- 主键查询：直接进聚簇索引，最快
- 走二级索引的查询：**只有需要的数据在二级索引里拿不全时**，才需要回表
- 覆盖索引：不需要回表
- 全表扫描：连索引都不走，直接把表（聚簇索引叶子）全读一遍
--------------------------------------------------------------------
- 条件是主键 → 走聚簇索引，不进二级索引
- 条件是非主键列且建了索引 → 走二级索引，可能要回表
- 条件是非主键列且没建索引 → 全表扫描
- 查询返回的列二级索引全覆盖 → 走二级索引但不回表
-----

##### limit 优化
![[Pasted image 20260807101101.png]]

这一章节还是我来进行分析吧，假设id不是主键且没有建立索引
SELECT * FROM t_user ORDER BY id LIMIT 1000000, 20;
如果是上述的sql语句执行，那么会出现回表查询，而且order by会导致mysql首先会进行file sort这一步也就十分耗时，然后在limit 1000000这个阶段，select在limit执行之前，所以还是把所有的数据进行返回。

所以我们的思路就很明确了，首先尽量id建立一个索引，这样我们就不需要把时间耗在sort上。然后select我们不需要前1000000的所有数据，我们要的是后部分的数据，所以select * 前面就可以省略了，因此我们可以采用。

SELECT t.*
FROM t_user t
JOIN (
  SELECT id
  FROM t_user
  ORDER BY id
  LIMIT 1000000, 20 // 先通过id进行查表，返回一个id子表，也就是**延迟关联**
) tmp ON t.id = tmp.id;// 然后用一个id进行匹配返回对应的数据

如果业务是“下一页 / 上一页”，根本不用 offset，记住上一页最后一条的 id 就行：

一页最后一条记录的 id = 1000000
SELECT * FROM t_user
WHERE id > 1000000
ORDER BY id
LIMIT 20;

##### 行级锁
![[Pasted image 20260807162039.png]]
**行锁**：
![[Pasted image 20260807163001.png]]![[Pasted image 20260807163048.png]]![[Pasted image 20260807163611.png]]
这里要注意一下，如果你的DML在检索的时候，没有根据索引进行查询，那么此时行锁就会升级为表锁。如果select 语句加了锁，同样也会变成表锁。一句话总结：**普通 SELECT 永远不加锁；会“锁全表”的是当前读（FOR UPDATE/FOR SHARE）和 UPDATE/DELETE，而且本质是“全表扫描逐行加锁”，不是真正的表锁升级。**

**间隙锁/临键锁（nexy-key锁）**
![[Pasted image 20260807164740.png]]

```
-- 事务A
SELECT * FROM student WHERE id > 20 FOR UPDATE;
-- 第一次查询，看到 30

-- （此时如果事务B插入 id=25）
-- 第二次查询，会多出一行 25 → 幻读
```

| 场景                            | 加的锁                 |
| ----------------------------- | ------------------- |
| 唯一索引等值且命中，`id = 20`           | 只锁记录 20             |
| 唯一索引等值但没命中，`id = 25`          | 只锁间隙 (20,30)        |
| 范围查询，`id > 20`                | 临键锁 (20,30]、(30,+∞] |
| 普通索引等值，`name = '小明'`（可能有多个小明） | 每个小明周围的临键锁          |
| 没走索引的 UPDATE / FOR UPDATE     | 锁全表扫描到的所有记录+间隙      |

**1. 普通 SELECT：默认不加锁（快照读）**

```
SELECT * FROM student WHERE name = '小明';
```

在 RU、RC、RR 三个级别下，普通 SELECT 都走 MVCC 快照读，不申请行锁、间隙锁、临键锁。它只读历史快照，既不阻塞别人，也不被别人阻塞。

唯一的例外是 **SERIALIZABLE + autocommit=0**：此时普通 SELECT 会被自动变成共享锁读（FOR SHARE），才会加锁。

**2. UPDATE / DELETE：默认必加锁（当前读）**

UPDATE 和 DELETE 天然是“当前读”，不需要你写 `FOR UPDATE`，它们**一定会加锁**。加什么锁，由“隔离级别 + 索引使用情况 + 条件类型”决定：

|情况|加的锁|
|---|---|
|主键/唯一索引等值且命中，如 `WHERE id = 20`|记录锁（只锁 20）|
|主键/唯一索引等值但未命中，如 `WHERE id = 25`|间隙锁 (20,30)|
|范围条件，如 `WHERE id > 20`|临键锁（RR 下）|
|普通索引等值，如 `WHERE name = '小明'`|每个小明周围的临键锁|
|没走索引，如 `WHERE name = 'xx'`（无索引）|扫描到的所有记录 + 间隙都锁（近似锁全表）|

**3. 隔离级别会影响“锁哪些”**

- **RR（默认）**：间隙锁、临键锁默认开启，能防幻读，代价是锁的范围大
- **RC**：间隙锁被禁用（外键检查和唯一性检查除外），只加记录锁，锁范围小、并发好，但可能出现不可重复读/幻读
- 所以“UPDATE 默认加临键锁”这句话**只在 RR 下成立**，RC 下基本只有记录锁
