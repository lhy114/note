# Redis 作为一个高性能的原子计数器。
## 秒杀问题
### 全局ID生成器
![[Pasted image 20260827201731.png]]![[Pasted image 20260827201943.png]]
这不就是雪花算法吗?
![[Pasted image 20260819143242.png]]雪花算法（Snowflake）是用来**生成全局唯一、趋势递增的分布式 ID** 的，典型用途就是分布式系统里的主键。

**为什么需要它**

单机数据库可以用自增 ID，但分布式系统里多个服务、多台机器各自生成 ID，容易冲突。雪花算法让不同机器各自生成 ID 也不会重复，同时还能保证大致有序。

**ID 的构成（64 位 Long）**

```
1位符号位 | 41位时间戳 | 10位机器ID | 12位序列号
```

- 符号位：固定 0。
- 时间戳：记录生成时间，保证 ID 随时间递增。
- 机器 ID：区分不同机器，防止跨机器冲突。
- 序列号：同一毫秒内最多生成 4096 个 ID，超出则等下一毫秒。

**特点**

- 全局唯一，不依赖数据库。
- 趋势递增，比 UUID 更有利于数据库索引，尤其 InnoDB 主键。
- 生成速度极快，高并发下每毫秒每台机器可生成几千个。
- 纯内存计算，不需要网络交互。

|1|雪花算法|Redis ID|
|---|---|---|
|生成位置|本机|Redis服务器|
|依赖网络|❌|✅|
|性能|极高|较高|
|实现难度|较复杂|简单|
|唯一性|机器ID保证|Redis单线程保证|
|是否依赖中间件|否|Redis|
|是否趋势递增|是|是|
|适合大规模|非常适合|一般|

              一人一券
                 │
        ┌────────┴────────┐
        ↓                 ↓
      加锁             唯一索引
        │                 │
防止并发请求同时       数据库最终保证
通过 count 检查        不能出现重复订单

这里教程给了一个加锁的情况,我们在补充一个唯一索引进保障,当然还有其他方法我们后续补充.


#### 乐观锁与悲观锁的选择
乐观锁能不能解决，不取决于“查询的是 count 还是其他东西”，而取决于：你有没有一个可以被原子比较的“版本/状态”，并且把“检查 + 修改”绑定成一个原子操作。

“检查条件 + 修改数据”这个关键动作必须由某个并发安全的操作一次完成。


#### 乐观锁的理解

> 乐观锁的核心不是“更新/删除操作”，而是**检查后准备执行的操作能否原子化**。

- 乐观锁：先查询版本号，更新时再次判断版本号是否变化。
    
- 如果**检查 + 更新**能够原子化，那么检查结果和后续操作之间就不存在并发插入的时间窗口。
    
- 如果只是 `count → 判断 → insert`，即使再次查询 `count`，也无法保证检查之后不会有其他线程插入，因此单纯依靠 `count` 无法实现可靠的乐观锁。
    
- 如果强行把 `count → 判断 → insert` 整个流程锁成一个原子过程，本质上就变成了**悲观锁**。
    
- 因此，一人一券这种场景，更自然的思路是：**不去保证 `count` 的判断，而是直接保证 `insert` 不能重复**，例如数据库唯一索引。
    

> **核心：乐观锁的关键是“检查条件 + 后续操作”的原子性；`count` 本身无法解决这个问题，而唯一索引可以直接约束最终的 `insert`。**


看到并发问题 → 找到“检查 + 修改”的竞态窗口 → 想办法让关键判断和修改成为一个原子操作 → 优先利用数据库/Redis提供的原子能力；实在无法原子化，再考虑加锁。

### 分布式锁
三个核心要求

1. **基础的加锁、解锁操作**
    - 加锁：`SETNX + TTL`
    - 解锁：删除 Redis Key
    - 
2. **锁必须属于当前线程**
    
    - 不能直接 `DEL`，否则可能误删其他线程的锁。
    - 因此需要给锁设置唯一标识，例如：
    
    ```
    UUID + ThreadId
    ```
    
3. **加锁、解锁过程要保证原子性**
    - 加锁需要保证“判断不存在 + 创建 + 设置过期时间”整体完成。
    - 解锁需要保证“判断 value 是否属于自己 + 删除”整体完成。
    - 因此解锁使用 **Lua 脚本**，避免判断和删除之间出现并发问题。

MultiLock 要求所有节点加锁成功，是因为它把多个 Redis 锁组合成一个整体；只允许部分成功会导致不同客户端分别持有不同节点的锁，从而无法保证整体互斥。

> “那为什么不采用部分节点成功，比如多数节点成功？”

这个思路其实是**另一种分布式锁设计思想**，也就是你以后可能会听到的：

> **Quorum / 多数派**

例如：

```
5个节点

3个成功 → 算成功
```

这和：

```
MultiLock：
A+B+C+D+E 全部成功
```

是**两种不同的设计**。

所以不要认为：

> “MultiLock 全部成功，所以分布式锁必须全部成功。”

不是。

而是：

> **Redisson MultiLock 选择了“全部锁实例成功才算成功”的语义。**
