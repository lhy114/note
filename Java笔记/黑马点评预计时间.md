# 达人探店
预计时间: 1-2小时
实际时间:2小时, 最主要的原因是由于重置redis之后发现,在秒杀任务的stream流被我删除了,补上之后 处理订单的那一个线程并没有安全的暂停,因此我们采用了

@PreDestroy  
public void shutdown() {  
    running = false;  
    SECKILL_ORDER_EXECUTOR.shutdownNow();  
}

在运行结束前,让这个线程关闭, 同时代理的这个方法,我们也就进行了改造, 利用懒加载的方法进行实现@Lazy  
private IVoucherOrderService proxy;

**后台线程为什么停不下来**
- `Executors.newSingleThreadExecutor()` 创建的是非守护线程，任务又是 `while(true)`，所以主程序停止后 JVM 还被它拖着。
- 修复组合：守护线程工厂 + `while(running)` + `@PreDestroy` 中 `shutdownNow()` + 异常处理不再无限递归，失败时 sleep 后再重试。

但是设置守护线程也不好，它不保证“线程跑完”，而是保证“进程一定能退出”。

但订单消费线程的业务语义是：**尽量把消息处理完、确认完再退出**。如果进程正在处理一笔订单，突然因为 JVM 退出被守护线程机制杀掉，这笔订单就可能处理到一半：

- 库存可能扣了，但订单还没落库
- 消息可能没 ACK，流程中断

虽然 Redis Stream 的 pending 消息还能在下次启动时重新消费，但这属于“事后补偿”，不是正常退出路径。

也就是说在最初代码中,其实有一个问题,主线程启动后,秒杀的这个线程也自动创建,但是并没有一个销毁的动作.

你点击停止程序时，Spring 开始关闭上下文，会销毁 Redis 的连接工厂 `LettuceConnectionFactory`。但此时这个后台线程并不知道应用要退出，它还在 `while(true)` 里继续跑，下一次又去调 Redis。

于是就会发生：
1. 主线程停止 Spring 上下文
2. Redis 连接工厂被销毁
3. 秒杀线程仍然在 run() 里循环
4. 它再次调用 Redis -> 连接工厂已经销毁，抛异常
5. catch 捕获异常并打印“处理订单异常”
6. 旧代码里 catch 又递归调用 handlePendingList，继续读 Redis
7. 于是错误不断重复，甚至爆栈
