# 秒杀活动
预计:2个小时
实际:8个多小时,最主要的就是多线程、并发问题,线程池原因. 全局id好解决,秒杀下单,用乐观锁进行实现(最主要的就是,一开始jmx不太会用,虽然现在也不会,但是知道怎么做的). 一人一锁问题, 多种方法的不断改进, 首先就是基础的锁(其实一开始想的是任然用乐观锁进行实现,发现这个代码写了count不对劲,实现不了,或者很麻烦,需要吧这个操作变成原子操作才行,索性直接用悲观锁,其实也可以用一个唯一索引解决,利用的是insert的原子👍,然后对查询一人一单的时候主要解决的并发问题的细粒度问题,同时就是spring的代理问题), 然后这个锁存在一些问题(每一个人只能解自己的锁, 这时候要用userid进行实现,同时并发问题的细粒度问题,从方法加锁,到userID加锁, spring代理事务的问题,要手动代理).  然后基于这个实现了分布式锁的问题. 为什么要采用分布式锁的,主要的就是不同进程(注意是不同进程),他们的不同线程仍然会造成冲突,最主要的缺乏一个统一管理锁(也就是jvm的问题了),因此又用redis模拟了分布式锁, 一开始直接加锁就行了,但是发现了一个问题,就是判断销毁锁的时候,这个操作不是原子操作(为什么不是创造锁的时候,因为setnx能够实现我们的需要,但是delete操作满足不了),容易被打断,因此我们就基于lua脚本实现这个东西. 然后就是分布式的一些优化
