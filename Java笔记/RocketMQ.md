## 优点和缺点
### 优点
1. 应用解耦, 说人话: 就是之前一个订单业务是同步的, 如果要执行完毕, 就要一次执行库存系统、支付系统、物流系统等, 带来的问题就是, 延迟较高, 这个业务与其他业务高耦合, 如果你还要添加一个新的功能就要重新写一个业务加入到订单系统中
2. 异步提速, 同理一, 提高了速度
3. 削峰填谷, 也就是当一个**缓存**, 将用户的请求存储到mq中

### 消息的顺序
![[Pasted image 20260911111917.png]]
![[Pasted image 20260911111741.png]]
由于一个topic里面有多个队列,这就导致了一个完整的业务流程可能分布在不同的队列里面, 这样每一个队列的处理的线程就会导致结果不同, 因此我们希望对于一个业务来说应该前面的消息应该也要顺序完成才对.

**那么我就产生了一个疑问 : 对于有多个步骤的业务, 如果直接采用默认的生产者发送消息, 会导致中间的某一步发送到不同的topic子队列中去, 此时消费者来进行消费会导致, 业务完成的顺序不同, 因为我们需要将同一个业务尽量放到同一个队列中去. 但是我的学习资料里面, 也把消费者设置了一个让同一个线程监听同一个queue, 我个人感觉没啥必要啊, 因为我只需要保障这个业务的顺序完成的一样, 至于是谁完成, 我觉得没有必要啊**

因为**Queue 只是“存储顺序”有序，不代表“处理过程”一定是串行的**。

举个最直观的例子。

假设 Queue 里已经按照顺序放好了：

```
Queue 1：

① → ② → ③
```

这时候来了 **3 个消费者线程**：

```
Thread A
Thread B
Thread C
```

消费者从 Queue 里取消息：

```
① → Thread A
② → Thread B
③ → Thread C
```

注意：**取消息的顺序仍然是 ① → ② → ③。**

但是取出来之后，三个线程就各自执行了：

```
Thread A：处理① ───────────────→ 完成

Thread B：处理② ─────→ 完成

Thread C：处理③ ─────────→ 完成
```

由于三个线程是**并发执行**的，所以实际完成顺序可能是：

```
① 开始
② 开始
③ 开始

② 完成
③ 完成
① 完成
```

因此除了保障你要存放的在一个queue里面, 还要保障并发的问题


生产端：syncSendOrderly + 相同 hashKey
消费端：consumeMode = ConsumeMode.ORDERLY

|内容|作用|
|---|---|
|`RocketMQHeaders.KEYS`|业务查询、排查、追踪|
|`hashKey`|选择消息队列，决定同 key 是否进同一个队列|
|`consumeMode = ORDERLY`|决定同一个队列是否串行消费|

### 事务消息
![[Pasted image 20260911122937.png]]![[Pasted image 20260911123010.png]]

```
1. 创建订单并写入订单表
2. 订单写库成功
3. 向 MQ 发送“订单创建成功”事件
4. 库存、营销、物流等服务异步消费
```

如果第 1 步成功，第 3 步失败，就会造成订单已存在但下游完全不知道。事务消息就是解决这个问题的。
