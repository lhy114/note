
## 一、以后不要凭感觉评价自己

最重要的一条：

> **不再问“我行不行”，改问“我实际做到什么程度”。**

比如不要说：

> “我 Java 应该学得挺快吧。”

而是记录：

> Spring Boot 基础预计 3 天 → 实际 5 天  
> Redis 基础预计 2 天 → 实际 3 天  
> 一个 CRUD 模块预计 1 天 → 实际 2 天

连续记录几周以后，你会开始知道：

> **“我正常情况下完成一个中等任务大概需要多久。”**

这比任何自我评价都可靠。

---

# 二、任何新任务都先做“小实验”，不要直接做计划

这是解决“我不知道自己能力如何”的最好方法。

比如：

> “我要做一个 Java Web 项目。”

不要直接计划：

> “一个月完成。”

先拿一个小模块：

> **用户登录模块**

然后给自己：

> 2 天。

看实际情况。

可能：

> 第一天半天看代码，半天修改；第二天完成。

那你以后就知道类似模块大约需要 1～2 天。

如果用了 5 天：

> 不是你能力不行。

而是：

> **第一次估算偏乐观。**

下一个类似任务按 5 天估。

---

# 三、给任务增加“完成标准”

你很容易犯的一个问题是：

> **不知道什么时候算完成。**

所以所有事情都先定义 Done。

例如：

### Redis 学习

不是：

> “把 Redis 学完。”

而是：

> 会基本数据结构  
> 会 Spring Boot 集成  
> 会缓存  
> 能解释缓存穿透/击穿/雪崩  
> 能在项目里使用

达到：

> **Done**

就停。

不要继续：

> “Redis 源码我是不是也应该看看？”

---

### Java 项目

定义：

> 能运行  
> 核心业务完整  
> MySQL  
> Redis  
> MQ  
> 登录鉴权  
> 能部署  
> 能讲清架构  
> 能回答项目问题

达到这个标准：

> **完成。**

剩下的优化属于“加分项”，不是“未完成”。

# 四、用“四级能力表”判断自己

以后学任何东西都问：

|等级|含义|
|---|---|
|L1|知道它是什么|
|L2|能跟着文档/教程使用|
|L3|能独立完成实际任务|
|L4|能解释原理、排查问题、优化|

然后**先确定岗位需要哪一级**。

例如你当前找 Java 实习：

> Spring Boot：L3 + 部分 L4  
> Redis：L3 + 常见 L4  
> MQ：L2～L3  
> 微服务：L2～L3  
> JVM：L2 + 常见问题 L3

这样你就不会因为：

> “我还没完全掌握 JVM”

而产生巨大焦虑。

因为你真正需要的可能只是：

> **达到面试和项目要求的水平。**

# 五、建立“预计时间 vs 实际时间”数据库

我认为这是你最值得长期坚持的一件事情。

建一个非常简单的表：

|日期|任务|目标|预计|实际|结果|
|---|---|---|---|---|---|
|8/26|Spring IOC|看懂+会用|3h|4h|完成|
|8/27|Redis|基础+项目接入|2d|3d|完成|
|8/30|登录模块|完整实现|2d|2.5d|完成|
|9/2|八股|50题|3h|4h|完成|

**不要记录“我今天努力不努力”。**

只记录：

> **我估计自己需要多久，我实际上用了多久。**

一个月以后，你会得到一个非常有价值的结论：

> “我通常会低估任务 30%。”

那么以后所有任务：

> **估算 × 1.3**

你的计划就会越来越准确。

# 六、不要只记录成功，也记录“为什么偏差”

比如：

> 预计 2 天 → 实际 5 天。

不要写：

> “我效率太低。”

写：

> **原因：第一次接触 Spring Security + 项目代码复杂 + 环境问题。**

这样你才知道下次应该怎么调整。

可能发现：

> 新技术第一次接触，我通常需要额外 50%。

那么下一次你自然就会留缓冲。

这叫**校准能力**。

---

# 七、对“新事物”的判断，用一个固定流程

你说自己最大的困难之一是：

> **面对新事物，不知道怎么判断。**

以后不要直接决定“学还是不学”。

先问：

### ① 它和我当前目标有什么关系？

比如 Agent：

> 当前目标：第一份 Java 实习。

所以结论：

> **现在不是主线。**

### ② 岗位真正要求我做到什么程度？

看 JD。

### ③ 我目前是什么等级？

L1 / L2 / L3 / L4。

### ④ 差距有多大？

比如：

> L2 → L3

### ⑤ 用最小实验验证需要多久？

> 做一个小 demo。

然后再决定：

> 值不值得继续。

这样你就不会看到一个新技术：

> “卧槽，这个我还没学。”

然后立刻把它加入计划。

---

# 八、最重要：不要用别人的速度校准自己

以后尽量不要：

> “别人三天学完，我五天才学完。”

因为你根本不知道：

- 对方之前有没有基础；
- 他学到什么程度；
- 是否真的掌握；
- 有没有项目经验。

你真正应该比较的是：

> **上个月的自己。**

例如：

> 以前一个 Spring 模块要 5 天，现在 3 天。

这就是明确的进步。

---

# 九、给自己设置“估算误差容忍区”

你现在特别容易因为计划偏差产生焦虑，所以我建议：

### 偏差 ≤ 20%

正常，不调整。

### 偏差 20%～50%

复盘估算方法。

### 偏差 > 50%

检查是不是：

- 任务拆得太粗；
- 难度判断错误；
- 基础不足；
- 范围过大。

**不要直接归因于“我能力差”。**
